# Command Center Template Library — strategy

The library is 40 independently designed templates across eight coordinated
design families, built from one component system, specified in one executable
registry, and generated by one toolchain.

## 1. The finding that shapes everything else

The platform already has a template system: `report_templates.schema`, rendered
by `src/lib/reportTemplate/`. It is a **fixed-page, absolutely-positioned canvas**
— pages have a fixed `{width, height}` in PDF points and hold blocks whose
overlays carry absolute `x`, `y`, `width`, `height`. There is no reflow, no
auto-grow, no overflow handling anywhere in the schema or the renderers.

That model is excellent at what it was built for: reconstructing an imported PDF
pixel-for-pixel, and letting a designer place elements on a canvas.

It cannot do what this library requires. The brief asks for templates that
accept "short paragraphs" or "multi-page written sections" in the same slot,
without text overlapping, tables leaving the page, or headings separating from
their content. An absolutely-positioned text box given twice its designed
content does exactly one of two things: it overflows, or it clips. Neither is
acceptable on a document a client receives.

**So the library introduces a second template model rather than extending the
first.** Two models, each doing what it is good at:

| | Canvas model (existing) | Flow model (this library) |
| --- | --- | --- |
| Layout | Absolute `x`/`y` in points | Document flow: stacked components |
| Built by | Visual editor, PDF import | Component composition in code |
| Content | Fixed-shape, designer-placed | Variable length, platform-injected |
| Strength | Pixel-perfect reproduction | Never breaks on unexpected content |
| Weakness | Breaks on unexpected content | Cannot reproduce an arbitrary PDF |
| Keep for | Imported client templates, marketing collateral, existing report builder | The 40-template library |

Both consume the same binding syntax (`{{path | filter}}`, `bindingResolver.ts`),
so one binding language and one data contract serve both. That is the
integration point; the layout engines stay separate.

### The alternative we rejected

We could have added auto-grow to the canvas model — measure text, expand the
box, push everything below it down. This is how a browser laid out documents
before CSS, and it fails in the same ways: two boxes on the same row grow
differently, a pushed element crosses a page boundary, and the "push down" logic
has to understand grouping, which is exactly the information an absolute
coordinate throws away. It is a reimplementation of flow layout on top of a
model designed to avoid it. Word, HTML and PDF all already have flow engines.
Use them.

## 2. Library structure

### Categories

| Category | Templates | Character |
| --- | --- | --- |
| Property & Buyer's Agency | 11 | Image-led, comparison-heavy, client-facing |
| Finance & Lending | 11 | Data-led, assumption-heavy, evidence-driven |
| Client Forms & Onboarding | 7 | Field-first, completable on screen or paper |
| Compliance & Governance | 6 | Auditable, status-driven, retained |
| Business & Advisory | 5 | Decision-led, options-and-recommendation |

The split follows where the work actually is. Property and finance carry the
most templates because those are the workflows the platform runs; business and
advisory carry fewest because a well-made executive report covers a wide range
of subjects and a fifth near-identical variant adds browsing cost, not value.

### Design families

Eight families, each carrying two to eight templates. **All eight share one
palette, one type scale, one geometry and one component library.** They differ
on the axes a reader actually perceives:

- **cover architecture** — band, panel, full-bleed, split, editorial, minimal;
- **density** — 0.88× to 1.32× base padding;
- **rule weight and fill strategy** — filled bands versus hairlines;
- **table treatment** — banded, hairline, ruled, boxed, ledger;
- **type pairing** — Cambria/Calibri, Georgia/Calibri, Arial, Calibri/Consolas.

This is the specific answer to "do not create 30 to 40 copies of the same design
with minor colour changes". The opposite failure — eight unrelated palettes — is
worse: it produces a clip-art pack, not a library, and it makes the white-label
system impossible because there is no single thing to re-skin.

### Naming and identity

Every template has a stable `id` (`property-investment-report`), a display name,
a one-line summary, and explicit "use this when" / "use something else when"
guidance naming the alternative template by id. That last field is the one most
libraries skip and the one that most reduces wrong selections: a user who lands
on the wrong card is told, on that card, where to go instead.

## 3. Design-system approach

### One component library, 47 components

Every template is composed from `scripts/aurixa-templates/components.py` and
nothing else. A reader who has learned what a recommendation box looks like has
learned it in all 40 templates; a developer wiring content injection binds
against a fixed set of shapes rather than 40 bespoke layouts.

Covers · section openers · dividers · executive summary · highlight, recommendation
and risk boxes · metric panels · info cards (client / organisation / property /
finance) · adviser profile · definition grids (display and input modes) · data,
comparison and status tables · native bar charts · chart frames · image frames
and galleries · map frames · timelines · process flows · checklists · document
control · signature and approval blocks · appendix openers · disclaimer pages ·
contact and back covers · table of contents · white-label panel.

### The flow guarantees

These are enforced in code and asserted by `verify_library.py`, not left to
designer discipline:

| Guarantee | Mechanism | Failure it prevents |
| --- | --- | --- |
| Content can always grow | Row heights are `atLeast`, never `exact` | Clipped text |
| Rows stay whole | `w:cantSplit` on every row | A field label on one page, its value on the next |
| Headers repeat | `w:tblHeader` on every data-table header | A 60-row register with no column labels on page 2 |
| Headings stay with content | `keepNext` on section openers and block headings | An orphaned heading at a page foot |
| Nothing escapes the margin | Fixed-layout tables at explicit millimetre widths derived from content width | Tables running off the page |
| Spacing is deterministic | Fixed-height spacer paragraphs, not margin collapse | Word, LibreOffice and Google Docs disagreeing on gaps |
| Optional sections are removable | Each section is a complete block preceded by its own spacing | Double gaps and orphaned headings after removal |

`verify_library.py` fails the build if any generated document contains an
exact-height row, a splittable row, or a captioned data table without a
repeating header.

### Typography

One type scale across all 40 templates. Families vary face, weight, tracking and
density — never the scale. Faces are limited to those that ship with Office on
Windows and macOS (Calibri, Cambria, Georgia, Arial, Consolas) so pagination is
stable on any machine that opens the file. A template that repaginates on the
recipient's laptop is a template that has failed, and no amount of typographic
ambition is worth that.

### Accessibility, by construction

- Body copy at 9.5pt minimum; nothing below 7pt.
- **Status is never colour alone.** Every status chip is a fill *plus* a glyph
  *plus* a word. A compliance document that only works in colour fails, because
  it will be printed and photocopied.
- Semantic colours (success / warning / alert / info) are excluded from
  white-label override in code. A partner palette that could turn a warning
  green would make the library actively dangerous.
- Data tables carry `w:tblCaption` and `w:tblDescription`, which assistive
  technology announces, and which the verifier uses to tell a data table from a
  layout grid.
- Alt text is a required binding on every image and chart frame; generation
  fails validation when it is empty.
- Risk ratings are words in table columns, never a coloured heat-map cell — a
  heat map is unreadable to assistive technology and meaningless in grayscale.

## 4. White-label architecture

Three layers resolve into what a component reads:

```
Palette          fixed Aurixa colour set          Aurixa design team owns
    +
DesignFamily     type, density, cover, tables     Aurixa design team owns
    +
BrandConfig      identity, contact, colour, level Partner organisation owns
    =
Theme            fully resolved
```

**A partner can supply colour, logo and copy. A partner cannot supply spacing,
type scale, margins or layout.** That is what makes "changing the brand
configuration does not damage the formatting" structurally true rather than
hoped for. There is no configuration a partner can set that reaches the layout.

### Four levels

| Level | Name | Cover | Footer | Metadata | Typical use |
| --- | --- | --- | --- | --- | --- |
| 1 | Aurixa Branded | Aurixa logo and name | "Aurixa Systems" | Aurixa | Platform collateral, Aurixa's own client work |
| 2 | Co-Branded | Partner logo primary, Aurixa lockup secondary | "Delivered with Aurixa Systems" | Aurixa | Partner onboarding, joint engagements |
| 3 | Partner Branded | Partner only | "Powered by Aurixa" | Aurixa | The default for most paying organisations |
| 4 | Fully White-Labelled | Partner only | none | none | Where contractually permitted |

Level 4 removes the Aurixa mark from document metadata as well as the body. A
"white-label" document whose `lastModifiedBy` says Aurixa is not white-labelled;
it is a document with a leak.

Each template declares `max_white_label_level`. Board papers and internal
serviceability workings cap at 3 — they are never issued under a partner brand
to an external audience — and the builder silently clamps rather than producing
a document that violates its own brief.

### The configurable surface

27 library-standard configuration points apply to every template, plus
template-specific extras (a credit licence number on lending recommendations, a
reporting-entity name on AML assessments, a second logo slot on partnership
proposals). Templates may add to the standard set; none may remove from it, so
an organisation configures its brand once and it applies library-wide.

The Aurixa master build of each template can carry an in-document **Brand &
Customisation Panel** listing every configurable area and where it appears — the
white-label surface made legible to a human who never opens the admin UI. The
generator strips it for partner builds.

## 5. User-selection experience

### Browse

A card grid, three across on desktop. Each card carries the cover thumbnail, the
name, the category chip, the one-line summary, the length band, data/image
intensity dots, the white-label ceiling, the version and last-updated date, and
a badge if the organisation has approved it.

Above the grid sit eight **curated shelves** — "Best for executive reports",
"Best for property-heavy reports", "Best for financial modelling", and so on.
These are curated, not computed. "Best for X" is a claim the design team should
own; deriving it from a scoring function produces confident nonsense the first
time the weights are wrong.

### Filter

Report type · industry · document length · design family · colour theme ·
formality · data intensity · image intensity · white-label level ·
client-facing or internal · export format. Filters are faceted with live counts,
because a filter that can return zero results without warning is a dead end.

Sort by relevance, recently used, most used in the organisation, newest, name.

### Recommend

`recommendTemplates()` in `src/lib/command-center/templateLibrary.ts` scores
templates against the shape of the user's request and content:

| Signal | Effect |
| --- | --- |
| Organisation-approved | +40, and −25 for everything else |
| Report-type match | +35 |
| Category match | +25 |
| ≥2 properties → a comparison template | +30 |
| ≥3 charts → a high-data template | +20, and −20 for a no-data template |
| Audience mode match (client-facing / internal / regulator / partner) | +15 |
| Content volume matches the length band | +15 |
| Formality match | +12 |
| Recently used | +10 |
| No generator yet | −3 |

**Every recommendation returns its reasons**, and the UI shows them. A
recommendation a user cannot interrogate is one they will not trust, and the
fallback — scrolling 40 cards — is worse than no recommender at all.

The same algorithm exists in Python (`registry.recommend`) so the toolchain can
regression-test recommendations without a browser.

### Select, configure, generate

1. Preview the full template — sample-content build, page by page.
2. Apply organisation branding (pre-filled from `whitelabel_settings`).
3. Choose a colour variation and white-label level.
4. Upload or confirm the logo; choose a cover image where the family supports one.
5. Enter client and project details, or bind them from an existing record.
6. Choose which optional sections to include — every optional section is
   removable without damaging document flow.
7. Reorder optional sections within their part of the document.
8. Generate; review the populated output; edit; export DOCX or PDF.
9. Optionally save as the organisation's default for that report type.

Steps 6 and 7 are driven by the `sections` array in the detail payload, which is
the same array the design brief is generated from.

## 6. Administration

Administrators need: create, duplicate, edit, archive, publish, unpublish;
assign to organisations and to subscription tiers; restrict by permission;
manage categories; upload previews; configure dynamic fields; define mandatory
and optional sections; set default branding; manage and roll back versions; test
content injection; preview DOCX and PDF output; approve before publication;
and track usage, exports, popularity and generation errors.

Two decisions matter more than the feature list:

**Templates are code, not data — until they are not.** The 40 library templates
are generated from `scripts/aurixa-templates/`, reviewed in pull requests, and
versioned in git. An administrator does not edit them in a UI, because a visual
editor over a flow-layout component system is a large product in its own right
and the library does not need one. What administrators *do* edit is the
**configuration** around a template: which organisations see it, which tier it
belongs to, which sections are mandatory, what the default branding is, and
whether it is published. Organisation-specific *derivatives* are stored as
configuration deltas against a library template, not as forked copies.

**Content-injection testing is a first-class admin feature, not a nice-to-have.**
Every template ships with a sample build produced by the *same* builder as the
master. An administrator can generate any template against sample data, a real
client record, or a deliberately hostile fixture (a 4,000-word executive
summary, a 200-row register, a client name of 90 characters, no images at all)
and see the output before publishing. Layout defects in generated documents are
found by trying to break them, not by looking at the happy path.

## 7. Content-injection methodology

### One binding language

`{{path.to.field}}` with optional `| filter`, matching
`src/lib/reportTemplate/bindingResolver.ts`. The canvas templates and the
library templates use the same syntax, the same resolver and the same filters,
so a data contract written once serves both.

### Section-level, not word-level

Narrative content binds as a **block**, not a paragraph: `{{report.executiveSummary}}`
resolves to an array of paragraphs of any length. This is the difference between
a template that survives real content and one that does not. A template with
`{{summaryParagraph1}}`, `{{summaryParagraph2}}`, `{{summaryParagraph3}}` has
silently decided the summary is three paragraphs.

The same applies to repeating content: a section marked `repeats` binds to an
array and emits one block per record, so a comparison of two properties and a
comparison of five use the same template.

### Master and sample from one builder

Each builder runs in two modes. `TOKENS` emits binding paths — the master the
platform injects into. `SAMPLE` emits representative content — used for design
review, admin injection testing, and library thumbnails. Building both from one
builder means a layout that passes review with sample content and breaks with
tokens cannot ship, because both are generated and verified on every build.

### Validation before generation

Generation fails, rather than producing a defective document, when a required
binding is missing, alt text is empty on an image or chart, a required section
has no content, or an image is below the template's stated minimum resolution.
Failing loudly at generation is recoverable; a client receiving a report with a
blank chart frame is not.

## 8. Commercial and subscription tiers

Current plan slugs are `launch`, `growth`, `scale` (see
`src/lib/pricing/planEntitlements.ts`); Enterprise is handled as a custom
arrangement.

| Tier | Templates | Branding | Administration |
| --- | --- | --- | --- |
| **Launch** | 8 foundational — client forms, verification, approval summaries | Logo, organisation details, one accent colour. White-label level 2 (co-branded) | Use published templates |
| **Growth** | +13 (21 total) — core property and finance reports | Full colour configuration, level 3 (partner-branded), custom disclaimers | Organisation defaults, favourites |
| **Scale** | +19 (all 40) | Level 4 where contractually permitted, per-report-type defaults, cover-image library | Approve templates, restrict by permission, usage analytics |
| **Enterprise** | All 40 plus bespoke | Bespoke design family, private categories | Private library, approval workflows, custom fields, API generation |

Tier assignment follows a principle: **templates that unblock onboarding are on
every tier.** A Launch customer who cannot produce a fact-find or a verification
summary cannot use the product at all, and gating those to force an upgrade
produces churn, not revenue. Gate the templates that represent premium *output* —
prestige presentations, development feasibility, portfolio review — not the ones
that represent basic *operation*.

### Beyond the tiers

Recommended, in order of margin and effort:

- **Bespoke design family** (Enterprise) — a ninth family in the organisation's
  own visual language, built on the same component system. High value, contained
  effort, because only the theme changes.
- **Template setup and branding service** — a fixed-fee onboarding engagement.
  The highest-conversion add-on, because the alternative is the customer
  discovering their logo looks wrong at 3× resolution on their first client
  report.
- **Industry bundles** — commercial property, SMSF, development finance. Sold as
  a pack rather than individually, so they are a positioning tool as well as
  revenue.
- **Annual refresh** — the library is re-cut yearly and subscribers get the new
  edition. This is the one that keeps the library from ageing, which is the
  main long-run risk to the whole feature.
- **Template migration** — converting an organisation's existing Word templates
  into the system. High effort per engagement; price accordingly and scope it
  tightly, because a customer's existing template is usually a canvas-model
  problem, not a flow-model one.

We would **not** recommend per-template purchases. They create a browsing
experience full of things the user cannot have, which measurably depresses
engagement with the things they can.

## 9. Risks and controls

| Risk | Why it matters | Control |
| --- | --- | --- |
| **Injected content breaks layout** | The single most likely way this feature loses trust | Flow layout throughout; `verify_library.py` fails the build on exact-height rows, splittable rows, or data tables without repeating headers; hostile-fixture testing in admin |
| **Spec drifts from the built artefact** | 40 briefs go stale within one release | Briefs are generated from the same registry the platform imports; the verifier asserts that every headed section in a brief exists in the built document under that exact title |
| **A partner re-skin damages the design** | Support burden and reputational damage | Brand config cannot reach spacing, type or layout; semantic colours excluded from override |
| **Semantic colour repurposed** | A "cleared" AML status rendered in a partner's red | Semantic colours are hard-coded and excluded from `BrandConfig` |
| **Grayscale or photocopy illegibility** | Compliance documents are printed and filed | Status carried by glyph + word + fill; family fills differ in lightness, not hue |
| **Accessibility regressions** | Legal exposure; unusable for some clients | Alt text is a required binding; data tables carry captions and repeating headers; no colour-only encoding |
| **Bundle bloat** | 40 full briefs is 417 KB of JSON | The bundled index is 98 KB and carries only what the grid needs; the long-form detail is fetched on demand; the verifier fails the build if the index exceeds 160 KB |
| **Compliance templates leaking to clients** | Serious | `audience_mode` drives portal visibility; internal and regulator templates are excluded from client-facing preview and share |
| **White-label leakage in metadata** | A level-4 document that says "Aurixa" in its properties | `set_properties()` omits the Aurixa attribution at level 4; add a metadata assertion to the export pipeline |
| **Library ageing** | A 2026 design language looks dated by 2029 | Annual refresh as a commercial product; families are re-cut by changing one dataclass, not 40 documents |
| **Two template models confuse users** | "Why can't I drag this?" | The canvas editor and the library are separate surfaces with separate entry points; a library template is never opened in the canvas editor |

## 10. What is built today

- **Toolchain** — `scripts/docgen/oxml.py` (schema-ordered WordprocessingML
  primitives), `scripts/aurixa-templates/` (theme, 47 components, registry,
  catalogue, builders, exporters, verifier).
- **Registry** — 40 templates fully specified, validating clean.
- **Generated artefacts** — the inventory, the family definitions, all 40
  briefs, the bundled TypeScript index and the fetched detail payload, all
  regenerated by one command.
- **Templates** — **all 40 built**, in master (binding token) and sample
  (populated content) form, from one builder each. Every design family, every
  category and every priority band is covered.

| Category | Built | Specified |
| --- | --- | --- |
| Property & Buyer's Agency | 11 | 11 |
| Finance & Lending | 11 | 11 |
| Client Forms & Onboarding | 7 | 7 |
| Compliance & Governance | 6 | 6 |
| Business & Advisory | 5 | 5 |
| **Total** | **40** | **40** |

Nothing in the catalogue is now specified-but-unbuilt. `verify_library.py`
asserts both directions of that relationship, so a template can neither be
published without a generator nor generated without a published brief.

The Cash-Flow & Net Position Report exercises the one layout capability the
other templates do not need: its eleven-column ledger is generated on a
**landscape section** with its own header and footer, because shrinking that
table to fit portrait would make it unreadable while still technically fitting.

```bash
python3 scripts/aurixa-templates/export_registry.py   # regenerate docs + registry
python3 scripts/aurixa-templates/build_library.py --sample
python3 scripts/aurixa-templates/verify_library.py
```
